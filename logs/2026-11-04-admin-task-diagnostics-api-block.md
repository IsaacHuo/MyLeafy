# 后台任务诊断查询阻塞生产 API

## 现象与边界

Admin 重构生产上线后，打开运行诊断会使 Node API 持续占用单核，社区和 `/health` 超时。独立监控记录了接口延迟、API 健康检查失败和任务快照不可用；服务器进程本身仍显示 active，不能用 systemd 状态代替业务健康。

临时恢复采用暂停采集、重启 API，并在网关短暂维护 `/api/admin/actions`，避免重复触发诊断；官网和 App API 保持服务。任务历史和业务数据库保留，未通过清空数据解决性能问题。修复发布及解除维护的实际结果见交付记录。

## 根因

`operationalHealth` 原查询对 `scheduled_runs` 的每一行执行一次同 job 的 `max(started_at)` 相关子查询。生产已有 56,781 条任务记录，重复全表扫描使同步 SQLite 查询长时间占用 Node 线程。先前离线样本任务较少，浏览器管理流程使用 mock，轻量 HTTP 负载没有执行真实任务诊断，因此未覆盖这一风险。

有上限的只读诊断在 200 ms 主动中断原查询；改为先按 job 聚合一次最大时间、再关联原行后，同一份生产任务元数据约 46 ms 返回四行。诊断没有写入生产数据，也没有读取学生内容。

新查询保留相同时间戳的并列记录及原响应字段，不改变鉴权、业务协议或数据库结构。

## 回归与交付要求

- 隔离样本加入 10,000 条任务历史、四种 job 和最新时间戳并列记录。
- 查询计划不得退回逐行相关聚合；结果保留全部最新记录和时间戳并列语义。
- 后端类型与业务回归、staging 完整检查、生产审批继续执行。
- 修复后需要在恢复的后台诊断入口上确认实际响应，并同时检查 App API，不能仅凭进程 active 或旧的浏览器 mock 验收宣布完成。
- 已完成的 30 分钟轻量负载结果只代表官网、健康和更新接口；不扩展为所有管理查询的数据规模验证。

额外 staging 实测在原有 50,962 条历史上加入 60,000 条隔离测试任务，通过真实 Cookie/CSRF 管理接口调用诊断约 282 ms 完成，并发健康请求最大约 223 ms。临时管理员、会话、审计和测试任务均在结束后清理。生产社区恢复已由所有者确认。

生产修复在所有者批准后经 Workbench 发布相同 staging 归档。版本 7e092f09ca64fa9d8cb836c03d982b818794818b，临时后台维护已解除；所有者再次确认诊断与社区正常。GHA 的传输失败和实际发布成功分开记录。
