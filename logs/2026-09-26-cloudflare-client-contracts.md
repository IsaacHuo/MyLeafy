# Cloudflare 迁移后的写入成功与客户端失败

## 症状与根因

纯文字帖已进入 Feed，发布队列仍提示“帖子创建后未能读取发布状态”。创建后状态查询原来只读取 pending_review，遗漏了无媒体帖会直接进入 published 的正常分支。客户端还会使用大写 UUID；D1 的文本匹配不具备 PostgreSQL UUID 类型的大小写规范化行为。

同类问题还可能出现在附件下载和评论读取：前一个权限查询规范化 ID，不代表后续 SQL 自动继承规范化后的值。应在每个 API 输入边界处理 UUID，并在后续查询中复用同一值。

## 恢复与幂等边界

- 发布队列重试先查询自己帖子的真实状态。published 表示成功，不能继续重新上传；隐藏或删除状态不能当成不存在。
- 数据库提交与网络响应不是同一件事。相同媒体 ID、路径、排序和所有者重放挂载时返回已经提交的结果，不重新消耗配额、插入媒体或发送通知。
- 已消费的验证凭证只能恢复原挂载，不能换 ID 挂载第二份。未消费但过期的凭证重新校验不可变文件后换发，旧凭证失效。
- 文件重新验证允许 uploaded/attached 状态，仍校验所有权、路径、大小、散列与结构。挂载前的写事务继续复核会话、发布权限和帖子状态。
- Swift 的 encodeIfPresent(nil) 表示省略字段，不能表示清空资料。PATCH 中需要清空的 bio/major/grade 必须发送显式 null。

## 接口核对方法

不能只统计已注册路由：要把真实客户端请求体、返回模型和数据库约束放在一起检查。举报分别发送 post_id/comment_id/reported_user_id，后台投票审核发送 decision。通知总未读数不能通过有限的一页结果推算。

回归用例在 backend/tests/，使用隔离 SQLite 重放 D1 schema；涵盖正常成功、响应丢失后的重复提交、拒绝路径、过期凭证与并发挂载。线上数据库检查只读取完整性、外键、身份关联、互动与评分计数、已发布媒体数量及清理失败记录，不在真实内容上构造写入测试。
